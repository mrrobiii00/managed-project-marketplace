# محتوای ارائه — مارکت‌پلیس پروژه‌های نرم‌افزاری

> ساختار پیشنهادی ۱۵ اسلاید + یادداشت ارائه‌دهنده. اعداد و وزن‌ها عیناً از پیاده‌سازی واقعی سیستم نقل شده‌اند (منبع: موتور تطبیق M07 و گزارش‌های میل‌استون).

---

## Slide 1 — عنوان پروژه

**مارکت‌پلیس پروژه‌های نرم‌افزاری**
پلتفرم مدیریت پروژه‌های نرم‌افزاری با تطبیق هوشمند متخصصان، مدیریت تیم و تسک، و نظام اعتبار — فارسی و RTL-first.

- ارائه‌دهنده / درس / تاریخ
- یک جمله: «از ثبت نیاز تا تحویل، با تطبیق شفاف و بازبینی انسانی»

## Slide 2 — مسئله (Problem)

- انتخاب متخصص/تیم نرم‌افزاری بر اساس **حدس و روابط**، نه داده
- **نبود شفافیت**: امتیاز و اعتبار متخصص قابل‌اتکا در دسترس نیست
- **بی‌برنامگی اجرا**: بدون تسک‌بندی، بدون پیگیری پیشرفت
- **بی‌اعتمادی پس از تحویل**: ارزیابی دوطرفه و سوابق ساخت‌نشده
- نتیجه: پروژه‌ها دیر، گران یا ناتمام تحویل می‌شوند

## Slide 3 — راه‌حل (Solution)

یک پلتفرم واحد با چرخه‌ی کامل عمر پروژه:

۱. کارفرما نیاز + بودجه + مهلت + مهارت‌ها را ثبت می‌کند
۲. **موتور تطبیق** متخصصان را امتیازدهی و رتبه‌بندی می‌کند (توضیح‌پذیر)
۳. مدیر تطبیق‌ها را بازبینی و تأیید می‌کند؛ تیم پیشنهادی شکل می‌گیرد
۴. اجرا با **تسک‌بندی و قواعد وضعیت** پیش می‌رود
۵. پس از تحویل، **ارزیابی دوطرفه** اعتبار طرفین را می‌سازد و در تطبیق‌های بعدی استفاده می‌شود

نکته‌ی کلیدی: **هیچ تصمیم خودکاری نهایی نیست** — انسان (مدیر) در حلقه است.

## Slide 4 — کاربران هدف (Target Users)

| کاربر | نیاز اصلی |
| --- | --- |
| **کارفرما (CLIENT)** | ثبت پروژه، دید شفاف تیم/پیشرفت، ارزیابی اعضا |
| **متخصص (SPECIALIST)** | دیدن پیشنهادهای متناسب، مدیریت پروفایل/مهارت‌ها، پیشبرد تسک‌ها، ساختن اعتبار |
| **مدیر سیستم (ADMIN)** | بازبینی و تأیید تیم‌ها، نمای عملیاتی کل سیستم |

## Slide 5 — معماری سیستم (System Architecture)

```
React + TypeScript (SPA فارسی/RTL)
        ↓  REST (JSON، پاکت استاندارد { success, message, data })
Node.js + Express + TypeScript (API لایه‌ای: routes → controller → service)
        ↓
Prisma ORM (type-safe، migration-managed)
        ↓
PostgreSQL
```

- **احراز هویت:** JWT (HS256، انقضا از env) + هش رمز با **Argon2id**
- **اعتبارسنجی ورودی:** Zod در هر مرز (auth/profile/project/task/rating)
- لایه‌بندی خالص: مسیر نازک، منطق دامنه در سرویس‌ها، قواعد در فایل‌های `*.rules.ts` قابل تست unit

## Slide 6 — طراحی دیتابیس (Database Design)

۱۲ جدول (PostgreSQL، نام‌گذاری snake_case از طریق Prisma `@map`):

- `users` / `profiles` / `skills` / `user_skills` (سطح مهارت + سابقه)
- `projects` / `project_skills` (الزامی/اختیاری) / `project_roles` (نقش × تعداد)
- `matches` (امتیاز ۶ مؤلفه + total + trust + وضعیت پیشنهاد)
- `teams` / `team_members` (نقش عضو + امتیاز تطبیق)
- `tasks` / `ratings`

**یکتایی‌های کلیدی (idempotency و یکپارچگی):** `users.email` · `UserSkill(userId,skillId)` · `Match(projectId,specialistId)` · `Team.projectId` · `TeamMember(teamId,userId)` · `Rating(projectId,fromUserId,toUserId)`

## Slide 7 — الگوریتم تطبیق (Matching Algorithm)

**گام ۰ — فیلتر سخت (Hard Filter):** متخصص باید حداقل یک مهارت **الزابی** پروژه را داشته باشد؛ وگرنه اصلاً امتیاز نمی‌گیرد (REJECTED بدون محاسبه).

امتیاز هر متخصص (۰ تا ۱۰۰) از ۶ مؤلفه‌ی وزن‌دار:

| مؤلفه | وزن | منطق (خلاصه) |
| --- | --- | --- |
| تطابق مهارت | **۴۰٪** | میانگین وزنی سطح مهارت‌ها (الزامی ×۳، اختیاری ×۱) — BEGINNER ۲۵ … EXPERT ۱۰۰ |
| تجربه | **۲۰٪** | سال‌های سابقه: ۰–۱→۲۰ … ۹+→۱۰۰ |
| پروژه‌های قبلی | **۱۵٪** | تعداد پروژه‌های تکمیل‌شده: ۰→۰ … ۴+→۱۰۰ |
| امتیاز کاربران | **۱۰٪** | میانگین rating ×۲۰ (بدون رتبه → ۵۰) |
| دسترس‌پذیری | **۱۰٪** | AVAILABLE→۱۰۰، در غیر این صورت ۵۰ |
| بودجه | **۵٪** | تطابق بودجه پروژه با نرخ متخصص |

سپس: **Total Score → Trust Score → وضعیت پیشنهاد**

- **Trust Score** = ۰.۷ × (بخش امتیاز کاربران) + ۰.۳ × (بخش پروژه‌های تکمیل‌شده) — شروع بدون سابقه (cold-start) = ۵۰
- وضعیت‌ها: Total < ۷۰ → **REJECTED** · Total ≥ ۸۵ **و** Trust ≥ ۸۰ → **RECOMMENDED** · در غیر این صورت **NEEDS_REVIEW**

نمونه‌ی واقعی دمو: پروژه‌ی «اپلیکیشن مدیریت تیم ریموت» → متخصص فرانت‌اند **۸۸.۵ / Trust ۸۲ → RECOMMENDED**؛ ۷ نفر از ۹ نامزد با فیلتر سخت حذف شدند.

## Slide 8 — تشکیل تیم (Team Formation)

- مدیر در بازبینی، تصمیم هر تطبیق را می‌گیرد: `APPROVE` / `REJECT`
- از تطبیق‌های تأییدشده، تیم با نام و نقش هر عضو ساخته می‌شود (`POST /admin/projects/:id/team`)
- امتیاز تیم = میانگین امتیاز اعضا؛ ذخیره و نمایش بدون بازمحاسبه
- چرخه‌ی وضعیت پروژه: `DRAFT → SUBMITTED → MATCHING → REVIEW → TEAM_PROPOSED → IN_PROGRESS` (شروع فقط از TEAM_PROPOSED)

## Slide 9 — مدیریت تسک (Task Management)

- تسک: عنوان، شرح، اولویت (کم/متوسط/زیاد)، مسئول، مهلت، وضعیت (`TODO → IN_PROGRESS → DONE`)
- **قواعد یکسان برای همه، مجوز متفاوت:**
  - کارفرمای مالک: ایجاد/ویرایش/حذف (فقط TODO) — بدون تغییر وضعیت
  - متخصص: تغییر وضعیت فقط تسک‌های خودش؛ ایجاد تسک خودتخصیصی
  - همه‌ی تغییرات فقط در پروژه‌ی IN_PROGRESS
- گذارهای نامعتبر (مثل DONE→TODO) با ۴۰۹ رد می‌شوند؛ پیش‌شرط تکمیل پروژه: حداقل یک تسک و همه DONE

## Slide 10 — ارزیابی و اعتبار (Rating & Reputation)

- پس از COMPLETED: طرف‌های پروژه (کارفرمای مالک ↔ اعضای تیم) یکدیگر را ارزیابی می‌کنند (۱ تا ۵ + دیدگاه اختیاری)
- هر جفت (پروژه، ارزیاب، ارزیابی‌شونده) فقط یک‌بار — یکتایی در سطح دیتابیس
- **موتور Reputation:** میانگین امتیاز، تعداد ارزیابی‌ها، پروژه‌های تکمیل‌شده، **Trust Score** (فرمول اسلاید ۷)
- اعتبار در تطبیق‌های بعدی به‌صورت خودکار استفاده می‌شود → چرخه‌ی ارزش: کار خوب → اعتبار بالاتر → پیشنهادهای بهتر
- نمونه‌ی دمو: متخصص فرانت‌اند → میانگین ۵ از ۵، Trust ۸۲

## Slide 11 — امنیت (Security)

- **JWT** با الگوریتم صریح HS256 و انقضای قابل‌تنظیم؛ توکن فقط در localStorage سمت کلاینت
- **Argon2id** برای هش رمز (بدون plaintext در DB)
- **RBAC**: نقش از توکن، گارد نقش روی هر مسیر (CLIENT/SPECIALIST/ADMIN)
- **محافظت IDOR**: دسترسی غیرمجاز به منابع دیگران → **404 یکنواخت** (بدون افشای وجود/عدم وجود)
- **مالکیت** در هر عملیات چک می‌شود (ویرایش/حذف فقط برای مالک)
- **Zod** روی همه‌ی ورودی‌ها → ۴۲۲ با پیام فارسی
- **Mass Assignment**: فیلدهای سیستمی (id/نقش/وضعیت/…) از payload ورودی strip می‌شوند
- **Rate Limiting**: مسیرهای auth (۳۰ درخواست/۱۵ دقیقه → 429)
- **Helmet** (CSP، HSTS، nosniff، frame-options) + **CORS کنترل‌شده** از env
- **خطاهای امن:** پیام عمومی فارسی برای ۵xx؛ stack trace فقط در development

## Slide 12 — فرانت‌اند (Frontend)

- React 18 + TypeScript strict + **Tailwind RTL** + React Router + fetch/Context (بدون کتابخانه‌ی state)
- **فارسی و RTL-first**: فونت وزیرمتن، `dir="rtl"`، اعداد و تاریخ فارسی
- کامپوننت‌های پایه‌ی یکدید (Button/Card/Badge/Input/Select/Dialog/Loading/Empty/Error)
- هر صفحه: **Loading / Empty / Error + تلاش مجدد** با پیام فارسی
- دسترس‌پذیری: label برای همه‌ی ورودی‌ها، aria-live، دیالوگ با Escape، radio بومی، focus ring
- Responsive: موبایل (drawer + کارت) تا دسکتاپ (جدول + سایدبار)
- **قاعده‌ی طلایی:** همه‌ی امتیازها verbatim از سرور؛ فرانت هیچ بازمحاسبه‌ای ندارد

## Slide 13 — دموی End-to-End

## ضمیمه A — توضیح یک‌دقیقه‌ای تطبیق (برای سؤالات)

«هر متخصص برای هر پروژه شش امتیاز می‌گیرد: مهارت (۴۰٪)، تجربه (۲۰٪)، پروژه‌های قبلی (۱۵٪)، امتیاز کاربران (۱۰٪)، دسترس‌پذیری (۱۰٪) و بودجه (۵٪). میانگین وزنی این شش مؤلفه امتیاز کل است. جدا از آن، اعتبار (Trust) از امتیاز کاربران (۷۰٪) و پروژه‌های تکمیل‌شده (۳۰٪) ساخته می‌شود. امتیاز زیر ۷۰ رد می‌شود؛ بالای ۸۵ با اعتبار حداقل ۸۰ "پیشنهاد مناسب" است؛ بقیه "نیازمند بازبینی". اگر متخصص حتی یک مهارت الزامی پروژه را نداشته باشد، اصلاً وارد محاسبه نمی‌شود.»
